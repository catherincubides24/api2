2 Descripción General del Sistema

2.1. ¿Para qué existe este sistema? (Pregunta Guía)

Huellitas Shop existe para digitalizar y optimizar de forma integral el proceso de comercialización y administración de suministros para mascotas (alimentos, juguetes, accesorios e higiene). El software unifica una experiencia de compra omnicanal rápida y responsiva para los dueños de mascotas con un centro de control operativo y financiero de alta precisión para los administradores y personal de la tienda.

2.2. Problemas que Resuelve

  • Desincronización de Inventarios: Previene la venta de productos sin existencias mediante transacciones concurrentes gestionadas por Spring Data JPA con bloqueo a nivel de base de datos.
  • Suplantación y Concurrencia Maliciosa: Impone una política de sesión única activa con latidos periódicos (`heartbeat`), invalidando accesos duplicados.
  • Ceguera Financiera y Administrativa: Proporciona generación instantánea de balances y reportes exportables a Microsoft Excel (`.xlsx`) y Adobe PDF (`.pdf`).
  • Falta de Trazabilidad Operativa: Almacena de forma inmutable un registro de auditoría (`logs`) ante cualquier cambio de precio, eliminación o actualización.

2.3. Usuarios Objetivo

Rol / Actor Nivel de Acceso Responsabilidades y Operaciones
CUSTOMER Cliente Externo Exploración de catálogo, carrito reactivo, compras vía PayPal o efectivo, descarga de tickets `HS-XXXXXX`.
EMPLOYEE Personal de Tienda Gestión y despacho de órdenes, confirmación de pagos en efectivo/transferencia, consulta de reportes y catálogo total.
ADMIN Administrador General Control total: CRUD de productos y usuarios, generación y restauración de backups SQL, auditoría de eventos y analítica.

2.4. Restricciones Técnicas

  • Zona Horaria Obligatoria: America/Bogota configurada en JVM, Hibernate JDBC, Jackson JSON y visualización frontend.
  • Moneda Oficial: Pesos Colombianos (COP) con formateo estandarizado de moneda sin decimales ambiguos.
  • Política de Sesión: Máximo una sola sesión abierta por usuario. Si se inicia sesión en otro dispositivo o ventana, la previa se revoca (código SESSION_REPLACED).
  • Inactividad: Expiración automática tras 2 minutos sin pulsaciones de actividad o heartbeat.

4 Arquitectura del Sistema

El sistema implementa una arquitectura Cliente-Servidor Desacoplada basada en microcontenedores coordinados por Docker Compose. El frontend es una Single Page Application (SPA) que interactúa de manera 100% asíncrona mediante peticiones HTTP/JSON contra una API RESTful Stateless protegida por tokens Bearer JWT.

Figura 4.1: Diagrama General de Componentes e Infraestructura de Huellitas Shop

4.1. Arquitectura por Capas en el Backend

  • Controller (Controladores REST): Expone los endpoints, maneja el protocolo HTTP y serializa/deserializa los DTOs.
  • Service (Capa de Lógica de Negocio): Aplica reglas de stock, políticas de sesión, validación de estados y transaccionalidad (`@Transactional`).
  • Repository (Persistencia): Interfaces Spring Data JPA con métodos derivados y optimizados.
  • Entity (Modelo de Dominio): Clases anotadas con Jakarta Persistence (JPA) que mapean a las tablas de PostgreSQL.
  • Audit & Security: Interceptores transversales que validan la sesión única y registran cada mutación en la base de datos de manera inmutable.

5 Módulos del Sistema

Cada módulo del sistema cuenta con una función específica, contratos de entrada y salida claros, y dependencias bien acotadas:

Módulo 1: Autenticación y Control de Sesión Core

Función: Registra clientes, autentica usuarios locales y con Google OAuth2, genera tokens JWT con claim de sesión única, y gestiona el cierre formal y pings de inactividad (`heartbeat`).

Entradas: RegisterRequest, AuthRequest, GoogleAuthRequest.

Salidas: AuthResponse (token JWT firmado, id, nombre, email, rol) o código 204 en logout/heartbeat.

Dependencias: UserRepository, UserSessionRepository, ActiveSessionService, JwtService, BCryptPasswordEncoder.

Módulo 2: Catálogo de Productos e Inventario Catálogo

Función: Permite consultar el catálogo público con filtrado y búsqueda por texto, así como el mantenimiento administrativo completo (creación, edición de precios/stock y borrado lógico/físico).

Entradas: Parámetros de consulta (`search`), ProductRequest con validación de precios positivos y stock.

Salidas: Lista de ProductResponse, objeto individual o respuesta de confirmación.

Dependencias: ProductRepository, AuditLogRecorder.

Módulo 3: Gestión de Pedidos y Tickets Transaccional

Función: Procesa el checkout de compras, descuenta inventario, calcula montos totales, genera comprobantes con identificador único HS-XXXXXX y gestiona el ciclo de vida del pedido (`PENDING`, `PAID`, `SHIPPED`, `CANCELLED`).

Entradas: OrderRequest (userId, lista de items con cantidad), OrderStatusUpdateRequest.

Salidas: OrderResponse con detalle de subtotal por ítem, TicketResponse.

Dependencias: PetOrderRepository, OrderItemRepository, ProductRepository, OrderSecurity.

Módulo 4: Pasarela de Pagos (PayPal & Efectivo) Pagos

Función: Orquesta la creación de órdenes en los servidores de PayPal, redirección segura a PayPal Checkout, captura de fondos autorizados y confirmación manual de pagos presenciales en efectivo.

Entradas: orderId, PaymentCaptureRequest (con `paypalOrderId`), PaymentUpdateRequest.

Salidas: PaymentOrderResponse (approveUrl), PaymentCaptureResponse.

Dependencias: PayPalService, PayPalCheckoutSDK, PetOrderRepository.

Módulo 5: Analítica y Reportes Ejecutivos Reportes

Función: Agrega métricas financieras (total facturado, ticket promedio, ventas por categoría y productos más vendidos) y exporta libros tabulares en formato Microsoft Excel y documentos PDF con membrete.

Entradas: ReportFilter (rango de fechas, categoría, estado), ReportFormat (`XLSX`, `PDF`).

Salidas: ReportSummary en JSON, o archivo binario en streaming con cabecera `Content-Disposition`.

Dependencias: ReportService, Apache POI (poi-ooxml), LibrePDF / OpenPDF.

Módulo 6: Auditoría, Trazabilidad y Backups Seguridad & TI

Función: Registra de manera automática e inalterable cada acción administrativa en la base de datos (`AuditLog`), proporciona consulta paginada de auditoría y permite realizar volcados y restauraciones completas en SQL.

Entradas: Eventos de Hibernate (`post-insert`, `post-update`, `post-delete`), archivo `.sql` multipart para restauración.

Salidas: Registros paginados de auditoría, archivo SQL descargable o estado de restauración.

Dependencias: AuditLogRepository, HibernateAuditListener, BackupService, JdbcTemplate.

9 Seguridad

Arquitectura de Seguridad en Profundidad
El sistema implementa mecanismos de defensa en múltiples capas, asegurando la confidencialidad, integridad y disponibilidad de la información conforme a las mejores prácticas de OWASP.
  • Autenticación y Criptografía: Cifrado de contraseñas mediante BCryptPasswordEncoder con salt dinámico por usuario. Generación de tokens JWT firmados con clave simétrica secreta (HMAC-SHA256) de longitud segura.
  • Control de Acceso por Roles (RBAC): Protección declarativa de métodos mediante @PreAuthorize con los roles ROLE_ADMIN, ROLE_EMPLOYEE y ROLE_CUSTOMER. Reglas de propiedad SpEL (@orderSecurity.ownsOrder(#id, authentication)) para evitar acceso horizontal no autorizado entre clientes.
  • Protección contra Inyección SQL (SQLi): Consultas 100% parametrizadas a través de Hibernate ORM y Spring Data JPA, impidiendo la concatenación dinámica de sentencias SQL maliciosas.
  • Mitigación de Cross-Site Scripting (XSS): El Virtual DOM de React escapa y neutraliza contextualmente todas las cadenas de texto renderizadas antes de insertarlas en el árbol DOM del navegador.
  • Mitigación de CSRF: Arquitectura REST Stateless con cabecera obligatoria Authorization: Bearer <token> sin uso de cookies vulnerables a cross-origin.
  • Control de Concurrencia e Inactividad: Servicio ActiveSessionService que fuerza la sesión única por cuenta de usuario y cierra la sesión tras 2 minutos de inactividad asistido por un InactivityGuard en el frontend.
  • Auditoría Inmutable: La entidad AuditLog no cuenta con métodos setters ni endpoints de modificación/borrado, garantizando un registro fidedigno de auditoría.

12 Mantenimiento del Sistema

12.1. Gestión y Monitoreo de Logs

Monitoreo de eventos en tiempo real mediante comandos nativos de Docker:

docker compose logs -f --tail=100 backend
docker compose logs -f db

12.2. Política de Respaldo y Recuperación (Disaster Recovery)

  • Frecuencia: Respaldos diarios en horario de bajo tráfico (02:00 AM America/Bogota).
  • Comando de Volcado Manual en Caliente: 
    docker exec -t petshop-db pg_dump -U postgres -d petshop_db -F c -b -v -f /var/lib/postgresql/data/backup_$(date +%Y%m%d).dump
  • Procedimiento de Restauración: Cargar el volcado a través del endpoint administrativo POST /api/backup/restore o mediante el cliente oficial pg_restore.

12.3. Escalabilidad Horizontal y Vertical

Gracias al diseño Stateless de la API (la autenticación se valida en cada petición mediante el token JWT y el registro de sesión en base de datos), el servicio backend puede escalar horizontalmente en múltiples instancias detrás de un balanceador de carga Nginx o Cloud Load Balancer sin pérdida de estado.

13 Recomendaciones y Conclusiones

Buenas Prácticas para el Equipo de Ingeniería
  1. Documentación Continua: Mantener actualizados tanto este manual técnico como los esquemas Swagger OpenAPI ante cualquier modificación de la API o la base de datos.
  2. Seguridad de Credenciales: Nunca versionar contraseñas, tokens de PayPal o secretos JWT en Git; utilizar siempre archivos .env ignorados o gestores de secretos.
  3. Consistencia Horaria: Asegurar que todo nuevo desarrollo preserve la zona horaria America/Bogota para evitar discrepancias en el cálculo de reportes de ventas.
  4. Pruebas Automatizadas: Ejecutar mvn test y npm run build antes de fusionar cualquier cambio a la rama main.
